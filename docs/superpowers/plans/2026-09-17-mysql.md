# MySQL on the tailnet — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run a standalone MySQL 8.4 server in the k3s cluster, reachable from a laptop anywhere on the internet at `mysql.<tailnet>.ts.net:3306` via the Tailscale operator, with no public internet exposure.

**Architecture:** A plain Kustomize base at `apps/mysql/` (namespace, Longhorn PVC, Deployment, Service) synced by a new Argo CD Application. The Service carries `tailscale.com/expose` annotations, so the already-running Tailscale operator creates an L4 TCP proxy and registers a tailnet device. The Cloudflare tunnel and Traefik are not involved — there is no Ingress in this app.

**Tech Stack:** k3s v1.35.5, Kustomize (via `kubectl kustomize`), Argo CD app-of-apps, Longhorn CSI, Tailscale Kubernetes operator, `mysql:8.4` official image.

**Spec:** [`docs/superpowers/specs/2026-09-17-mysql-design.md`](../specs/2026-09-17-mysql-design.md)

## Global Constraints

- Image is exactly `mysql:8.4`. Verified multi-arch on Docker Hub (`amd64` + `arm64` manifests both present) but pinned to amd64 anyway — see below.
- Every pod in this app sets `nodeSelector: kubernetes.io/arch: amd64`. The cluster is 3 amd64 HP EliteDesk control-plane nodes + 4 arm64 Raspberry Pi 5s; the InnoDB buffer pool goes on the minis.
- `storageClassName: longhorn`. Never `local-path` — the default StorageClass in this cluster is `local-path`, so it must be named explicitly.
- Namespace is `mysql`. Resource names are `mysql` (Deployment, Service), `mysql-data` (PVC), `mysql-secret` (Secret).
- Selector label is `app.kubernetes.io/name: mysql` everywhere.
- No `Ingress` resource, no Cloudflare tunnel public hostname, no Traefik route.
- Nothing is ever applied by hand except the Secret and the namespace. Argo CD owns the rest; `prune: true` and `selfHeal: true` are on.
- Secrets are never committed to git.
- There is no CI pipeline and no unit-test framework in this repo. The test cycle for every manifest task is `kubectl kustomize` (render) followed by `kubectl apply --dry-run=server` (real API-server validation against the live cluster). Treat a non-zero exit or unexpected output as a failing test.

- [ ] **Step 1: Create the namespace and the Secret by hand**

These two are the only things applied outside Argo CD. The Secret must exist
*before* the Deployment starts, or the pod sits in `CreateContainerConfigError`.

Pick a strong password — this is root, reachable from every device on your
tailnet.

```bash
kubectl create namespace mysql
kubectl -n mysql create secret generic mysql-secret \
  --from-literal=MYSQL_ROOT_PASSWORD='REPLACE_WITH_A_STRONG_PASSWORD'
```

Verify:

```bash
kubectl -n mysql get secret mysql-secret -o jsonpath='{.data.MYSQL_ROOT_PASSWORD}' | base64 -d | wc -c
```

Expected: a byte count matching your password length, not `0` and not an error.

> Note: `MYSQL_ROOT_PASSWORD` is read by the image's entrypoint **only when the
> data volume is empty**. Editing this Secret later does not change the
> password — that requires `ALTER USER` against the running server.

- [ ] **Step 4: Write `apps/mysql/deployment.yaml`**

Note the two env vars sourced from the same Secret key. `MYSQL_ROOT_PASSWORD`
is what the entrypoint reads on first boot; `MYSQL_PWD` is what the probes'
`mysqladmin` reads, so the password never appears in the container's process
arguments.

```yaml
# ─────────────────────────────────────────────────────────────────────────────
# MySQL 8.4 LTS — a standalone database for schoolwork. No cluster workload
# consumes it; its only client is a laptop on the tailnet.
#
# Access is root@'%', deliberately. That makes the tailnet ACL the real
# security boundary, not the MySQL grant table — any device that can reach
# tag:k8s can also DROP DATABASE. See the design note in
# docs/superpowers/specs/2026-09-17-mysql-design.md.
#
# Service DNS inside the cluster: mysql.mysql.svc.cluster.local:3306
# From the tailnet:                mysql.<tailnet>.ts.net:3306
# ─────────────────────────────────────────────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql
  namespace: mysql
  labels:
    app.kubernetes.io/name: mysql
spec:
  replicas: 1
  # ReadWriteOnce PVC — only one writer at a time, so never two pods at once.
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app.kubernetes.io/name: mysql
  template:
    metadata:
      labels:
        app.kubernetes.io/name: mysql
    spec:
      # The mysql:8.4 image publishes arm64, but the InnoDB buffer pool is a
      # poor fit for a shared Pi. The three amd64 minis have the headroom.
      nodeSelector:
        kubernetes.io/arch: amd64
      # The image starts as root and drops to the mysql user via its own
      # entrypoint (it chowns the datadir itself), so no custom securityContext.
      containers:
        - name: mysql
          image: mysql:8.4
          imagePullPolicy: IfNotPresent
          ports:
            - name: mysql
              containerPort: 3306
          env:
            # Read by the entrypoint ONLY on first boot, while the volume is
            # empty. Changing the Secret afterwards does not rotate it.
            - name: MYSQL_ROOT_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: MYSQL_ROOT_PASSWORD
            # Same value, read by mysqladmin in the probes below, so the
            # password never lands in the container's process arguments.
            - name: MYSQL_PWD
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: MYSQL_ROOT_PASSWORD
            - name: MYSQL_DATABASE
              value: school
            # Already the image default; set explicitly because it is the most
            # consequential property of this deployment.
            - name: MYSQL_ROOT_HOST
              value: "%"
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 1Gi
          # First boot initialises the data directory on a fresh Longhorn
          # volume, which is slow. The startup probe gives that up to 5 minutes
          # without a permissive liveness threshold afterwards.
          startupProbe:
            exec:
              command:
                - sh
                - -c
                - mysqladmin ping -h 127.0.0.1 -u root --silent
            periodSeconds: 10
            failureThreshold: 30
          readinessProbe:
            exec:
              command:
                - sh
                - -c
                - mysqladmin ping -h 127.0.0.1 -u root --silent
            periodSeconds: 10
          livenessProbe:
            exec:
              command:
                - sh
                - -c
                - mysqladmin ping -h 127.0.0.1 -u root --silent
            periodSeconds: 30
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: mysql-data
```

- [ ] **Step 5: Write `apps/mysql/service.yaml`**

```yaml
# ── MySQL on the tailnet ─────────────────────────────────────────────────────
# Deliberately NOT on the Cloudflare tunnel. A tunnel public hostname carries
# HTTP/HTTPS; the MySQL wire protocol is raw TCP, which a tunnel can only carry
# if every client machine first runs `cloudflared access tcp`. The Tailscale
# operator proxies L4 natively, so the client just connects.
#
# Same reasoning as the Pi-hole admin UI and the Longhorn UI.
# Reachable at mysql.<tailnet>.ts.net:3306.
apiVersion: v1
kind: Service
metadata:
  name: mysql
  namespace: mysql
  labels:
    app.kubernetes.io/name: mysql
  annotations:
    tailscale.com/expose: "true"
    tailscale.com/hostname: mysql
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: mysql
  ports:
    - name: mysql
      port: 3306
      targetPort: mysql
```

- [ ] **Step 6: Write `apps/mysql/kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

# Plain Kustomize base — consumed identically by Argo CD and Flux CD.
namespace: mysql

# ─────────────────────────────────────────────────────────────────────────────
# mysql — a standalone MySQL 8.4 server for schoolwork, on the tailnet only.
#
# BEFORE applying this stack:
#
#  1. Create the namespace:
#       kubectl create namespace mysql
#
#  2. Create the secret (NOT committed to git). Read on first boot only:
#       kubectl -n mysql create secret generic mysql-secret \
#         --from-literal=MYSQL_ROOT_PASSWORD="..."
#
#  3. Make sure the tailnet policy lets your devices reach tag:k8s — the same
#     grant the Pi-hole and Longhorn UIs already use.
#
#  There is no Cloudflare Tunnel hostname and no Ingress. This app is
#  reachable over the tailnet and nowhere else.
#
#  4. Apply:
#       kubectl apply -k apps/mysql/
#     or let Argo CD sync automatically after merging to main.
# ─────────────────────────────────────────────────────────────────────────────

resources:
  - namespace.yaml
  - pvc.yaml
  - deployment.yaml
  - service.yaml

labels:
  - pairs:
      app.kubernetes.io/part-of: homelab
    includeSelectors: false

# Keep only 2 old ReplicaSets/ControllerRevisions per workload instead of the
# Kubernetes default of 10. Without this the cluster accumulates dozens of
# empty ReplicaSets, and each retained revision pins its container image on the
# node — costly on the Pis, which have 28-58Gi disks.
patches:
  - target:
      kind: Deployment
    patch: |
      - op: add
        path: /spec/revisionHistoryLimit
        value: 2
  - target:
      kind: DaemonSet
    patch: |
      - op: add
        path: /spec/revisionHistoryLimit
        value: 2
```

- [ ] **Step 1: Write `bootstrap/argocd/applications/mysql.yaml`**

This is `_template.yaml.tpl` with every `<APP_NAME>` replaced by `mysql`, the
template's own instructional header dropped, and a note about the hand-made

```yaml
# ── Argo CD Application — mysql ───────────────────────────────────────────────
# A standalone MySQL 8.4 server for schoolwork, reachable over the tailnet at
# mysql.<tailnet>.ts.net:3306 and nowhere else.
#
# BEFORE this app can sync, create the Secret it reads on first boot:
#
#     kubectl create namespace mysql
#     kubectl -n mysql create secret generic mysql-secret \
#       --from-literal=MYSQL_ROOT_PASSWORD="..."
#
# Without it the pod stays in CreateContainerConfigError.
# ─────────────────────────────────────────────────────────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: mysql
  namespace: argocd
  # Argo CD will delete its own Application resource if the file is removed
  # from Git. It will NOT delete the deployed resources unless prune: true
  # is also set. Leave this in place for normal operation.
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/SilkePilon/homelab
    targetRevision: main
    path: apps/mysql
  destination:
    server: https://kubernetes.default.svc
    namespace: mysql
  syncPolicy:
    automated:
      prune: true       # delete K8s resources removed from Git
      selfHeal: true    # re-apply if someone manually modifies the cluster
    syncOptions:
      - CreateNamespace=true    # creates the namespace if it doesn't exist
      - ServerSideApply=true    # avoids annotation-size limits on large CRDs
```

- [ ] **Step 5: Confirm the volume and the pod**

```bash
kubectl -n mysql get pvc,pod
```

Expected:

```
NAME                               STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS
persistentvolumeclaim/mysql-data   Bound    pvc-...    10Gi       RWO            longhorn

NAME                         READY   STATUS    RESTARTS   AGE
pod/mysql-xxxxxxxxxx-xxxxx   1/1     Running   0          2m
```

`READY 1/1` is the important column — it means the readiness probe's
`mysqladmin ping` authenticated successfully, which proves the Secret was wired
through correctly.

First boot initialises the data directory and can take a minute or two; the
startup probe allows up to five.

- [ ] **Step 6: If the pod is not Running, read the actual reason**

```bash
kubectl -n mysql describe pod -l app.kubernetes.io/name=mysql | tail -30
kubectl -n mysql logs -l app.kubernetes.io/name=mysql --tail=50
```

Common causes, in order of likelihood:

| Symptom | Cause | Fix |
| --- | --- | --- |
| `CreateContainerConfigError` | `mysql-secret` missing or key misspelled | Re-run Task 1 Step 1; the key must be exactly `MYSQL_ROOT_PASSWORD` |
| `Pending`, event `didn't match node selector` | no schedulable amd64 node | Check `kubectl get nodes -L kubernetes.io/arch` |
| `Pending`, PVC stuck `Pending` | Longhorn has no room or is degraded | `kubectl -n longhorn-system get pods` |
| Log line `Access denied for user 'root'` in the probe | volume not empty, so the Secret password was never applied | This means the volume has prior data; the existing password still governs |

### Task 4: Tailnet reachability and persistence acceptance test

**Files:**
- Modify: none — this is the acceptance gate.

**Interfaces:**
- Consumes: the healthy deployment from Task 3.
- Produces: a confirmed working connection string for use from outside the LAN.

- [ ] **Step 1: Confirm the operator built a proxy for the Service**

```bash
kubectl -n tailscale get statefulset,pod
```

Expected: a new `ts-mysql-<suffix>` StatefulSet at `1/1`, alongside the
existing `ts-pihole-web-*` and `ts-longhorn-frontend-*`.

If no `ts-mysql-*` appears within a minute:

```bash
kubectl -n tailscale logs -l app.kubernetes.io/name=tailscale-operator --tail=50
```

The usual cause is the annotation value not being a quoted string — it must be
`tailscale.com/expose: "true"`, not `true`.

- [ ] **Step 2: Confirm the tailnet device registered**

Check <https://login.tailscale.com/admin/machines> for a device named `mysql`,
tagged `tag:k8s`. Note its full MagicDNS name — it will be
`mysql.<your-tailnet>.ts.net`.

- [ ] **Step 3: Connect from the laptop over the tailnet**

From the laptop (on the tailnet, but deliberately **not** on the home LAN if
you can manage it — tethering to a phone is the honest test):

```bash
mysql -h mysql.<your-tailnet>.ts.net -P 3306 -u root -p -e 'SELECT VERSION();'
```

Expected: prompts for the password, then prints a version string beginning
`8.4.`.

If it hangs or reports `Can't connect`: the tailnet policy does not grant your
device access to `tag:k8s`. This is the same grant the Pi-hole and Longhorn
UIs use, so confirm those are reachable from the same device before touching
the policy file.

If the client reports an authentication plugin error, the driver is too old for
`caching_sha2_password`. Upgrade the client — MySQL 8.4 does not ship the
`mysql_native_password` plugin by default, so there is no server-side
workaround.

- [ ] **Step 4: Write a row**

```bash
mysql -h mysql.<your-tailnet>.ts.net -P 3306 -u root -p school <<'SQL'
CREATE TABLE persistence_check (id INT PRIMARY KEY, note VARCHAR(64));
INSERT INTO persistence_check VALUES (1, 'written before reschedule');
SELECT * FROM persistence_check;
SQL
```

Expected: the `SELECT` prints the one row.

- [ ] **Step 5: Delete the pod and prove the data is on the volume, not the container**

```bash
kubectl -n mysql delete pod -l app.kubernetes.io/name=mysql
kubectl -n mysql get pod -w
```

Wait for a new pod to reach `1/1 Running`, then Ctrl-C.

> The Deployment uses `strategy: Recreate` on a ReadWriteOnce volume, so the
> old pod is fully gone before the new one attaches. Expect a short gap, not a
> rolling handover.

- [ ] **Step 6: Re-read the row**

```bash
mysql -h mysql.<your-tailnet>.ts.net -P 3306 -u root -p school \
  -e 'SELECT * FROM persistence_check;'
```

Expected: the same row. This is the real acceptance criterion — it proves the
Longhorn volume is carrying the data and that the tailnet name survives a pod
reschedule.

- [ ] **Step 7: Clean up the test table**

```bash
mysql -h mysql.<your-tailnet>.ts.net -P 3306 -u root -p school \
  -e 'DROP TABLE persistence_check;'
```

- [ ] **Step 8: Record the working connection details**

Nothing to commit. Note for yourself:

```
Host:     mysql.<your-tailnet>.ts.net
Port:     3306
User:     root
Database: school
Password: the value you put in mysql-secret
```

Requires Tailscale running on the client. A machine without it cannot reach
this server at all — that is the accepted tradeoff from the design.

## Follow-ups deliberately not in this plan

Both are called out in the spec's "Out of scope" section. Neither blocks the
work above.

- **`mysqldump` CronJob.** Longhorn replication survives a dead disk; it does
  not survive a bad `DROP DATABASE`, and root is reachable from every tailnet
  device. This is the obvious next change.
- **phpMyAdmin.** One more Deployment plus a second tailnet-annotated Service
  if a browser UI is ever wanted. Nothing here would need to change.
