# Pelican on the EliteDesks — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the Pelican game panel and its Wings daemon inside the k3s cluster on the three HP EliteDesk nodes, exposed on the LAN, so Minecraft servers can be created from the Panel UI and joined at `192.168.0.158:25565`.

**Architecture:** A Kustomize base at `apps/pelican/` with two Deployments. `pelican-panel` is a plain web app with SQLite on a Longhorn volume. `pelican-wings` is a two-container pod: the Wings daemon plus a privileged `docker:dind` sidecar that gives it a private Docker daemon on `127.0.0.1:2375`, because Wings only speaks the Docker Engine API and the nodes run containerd. Both are reached through k3s ServiceLB `LoadBalancer` Services, so every node IP answers. No Ingress, no tunnel, no tailnet.

**Tech Stack:** k3s v1.35.5 (native sidecar containers available), Kustomize via `kubectl kustomize`, Argo CD app-of-apps, Longhorn CSI, `ghcr.io/pelican/panel:v1.0.0-beta38`, `ghcr.io/pelican/wings:v1.0.0-beta29`, `docker:28.5.2-dind`.

**Spec:** [`docs/superpowers/specs/2026-09-22-pelican-design.md`](../specs/2026-09-22-pelican-design.md)

## Global Constraints

- Images are exactly `ghcr.io/pelican/panel:v1.0.0-beta38`, `ghcr.io/pelican/wings:v1.0.0-beta29`, `docker:28.5.2-dind`, `busybox:1.37`. All four tags verified present on their registries on 2026-09-22.
- Every pod sets `nodeSelector: kubernetes.io/arch: amd64`. Only the three HP EliteDesks are amd64.
- `storageClassName: longhorn` on every PVC. The cluster default is `local-path`, so it must be named.
- Namespace `pelican`. Resource names: Deployments `pelican-panel`, `pelican-wings`; Services `pelican-panel`, `pelican-wings`; PVCs `pelican-panel-data`, `pelican-wings-data`, `pelican-docker`; Secret `pelican-wings-config`.
- Selector labels: `app.kubernetes.io/name: pelican-panel` and `app.kubernetes.io/name: pelican-wings`.
- Panel is reached at `http://192.168.0.158:8088`. Wings is reached at `192.168.0.158:8080` (API) and `:2022` (SFTP). Game ports are `25565`–`25569`. None of these host ports are in use on any node today (checked: only 53, 80, 443, 8123, 9100, 29644 are claimed).
- The Panel container runs with `BEHIND_PROXY=true`. Without it Caddy takes its listen port and Host match from `APP_URL`, so it would listen on `:8088` and only answer `Host: 192.168.0.158`, which breaks probes hitting the pod IP. With it Caddy listens on `:80` for any Host.
- dind's `dockerd` is started with explicit `--host` flags so the image entrypoint does **not** add its default `tcp://0.0.0.0:2375` listener. The API must stay on loopback.
- Two mounts, `/var/lib/pelican` and `/tmp/pelican`, must appear at the **same path** in both the `wings` and `dind` containers. Wings asks dockerd to bind-mount those paths and dockerd resolves them in its own mount namespace.
- No `Ingress`, no Cloudflare tunnel hostname, no `tailscale.com/expose` annotation.
- Nothing is applied by hand except the Secret. Argo CD owns the rest with `prune: true` and `selfHeal: true`.
- Secrets are never committed to git.
- No CI, no unit-test framework. The test cycle for every manifest task is `kubectl kustomize` (render) then `kubectl apply --dry-run=server` (API-server validation against the live cluster). Non-zero exit or unexpected output is a failing test.
- Commit messages follow the repo's `type(scope): summary` style and end with the attribution line shown in each commit step.

```yaml
# ─────────────────────────────────────────────────────────────────────────────
# Pelican Panel — the web UI and API. https://pelican.dev
# Image: ghcr.io/pelican/panel:v1.0.0-beta38
# Port:  80 (Caddy + php-fpm inside the image)
# Data:  /pelican-data (SQLite DB, .env with APP_KEY, avatars, plugins)
#
# Reached at http://192.168.0.158:8088 via the pelican-panel LoadBalancer
# Service. No Ingress, no tunnel — see the design note in
# docs/superpowers/specs/2026-09-22-pelican-design.md.
#
# First run: open http://192.168.0.158:8088/installer. Choose SQLite,
# filesystem cache, filesystem session, database queue, and create the admin
# user. Then create a Node — see README.md.
# ─────────────────────────────────────────────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pelican-panel
  namespace: pelican
  labels:
    app.kubernetes.io/name: pelican-panel
spec:
  replicas: 1
  # ReadWriteOnce PVC and a SQLite file — never two pods at once.
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app.kubernetes.io/name: pelican-panel
  template:
    metadata:
      labels:
        app.kubernetes.io/name: pelican-panel
    spec:
      nodeSelector:
        kubernetes.io/arch: amd64
      # The image starts supervisord as root, which runs php-fpm as www-data
      # and chowns /pelican-data itself. No custom securityContext.
      containers:
        - name: panel
          image: ghcr.io/pelican/panel:v1.0.0-beta38
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 80
          env:
            - name: TZ
              value: "Europe/Amsterdam"
            # Every absolute URL the Panel generates (asset links, redirects,
            # the Wings config it hands out) is built from this.
            - name: APP_URL
              value: "http://192.168.0.158:8088"
            - name: APP_ENV
              value: "production"
            - name: APP_DEBUG
              value: "false"
            # Without this, Caddy reads its listen port AND Host match from
            # APP_URL: it would listen on :8088 and answer only
            # Host: 192.168.0.158, so a probe against the pod IP gets nothing.
            # With it Caddy listens on :80 for any Host, auto-HTTPS is off and
            # ASSET_URL is set to APP_URL. ServiceLB is, in effect, the proxy.
            - name: BEHIND_PROXY
              value: "true"
            # Where the image keeps state. Its entrypoint writes .env and the
            # SQLite file under here.
            - name: XDG_DATA_HOME
              value: "/pelican-data"
            # No mail server. Password resets land in the log instead.
            - name: MAIL_DRIVER
              value: "log"
          volumeMounts:
            - name: data
              mountPath: /pelican-data
            # Mirrors the upstream compose file: plugins live on the data
            # volume but the app expects them at this path.
            - name: data
              mountPath: /var/www/html/plugins
              subPath: plugins
            - name: logs
              mountPath: /var/www/html/storage/logs
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 1Gi
          # /up is Laravel's health route; the image's own HEALTHCHECK uses it.
          # First boot runs migrations and Filament optimisation on a fresh
          # Longhorn volume, which takes minutes — hence the startup probe.
          startupProbe:
            httpGet:
              path: /up
              port: http
            periodSeconds: 5
            failureThreshold: 60
          readinessProbe:
            httpGet:
              path: /up
              port: http
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /up
              port: http
            periodSeconds: 30
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: pelican-panel-data
        - name: logs
          emptyDir: {}
```

```yaml
# ── Panel on the LAN ─────────────────────────────────────────────────────────
# type: LoadBalancer, served by k3s ServiceLB (klipper). It runs a DaemonSet
# that claims host port 8088 on EVERY node, so any node IP reaches the Panel
# regardless of which EliteDesk the pod is on. Same mechanism as pihole-dns.
#
# externalTrafficPolicy: Cluster — every node answers, at the cost of the
# source IP being masqueraded. Nothing here needs the real client IP.
#
# Deliberately NOT on the Cloudflare tunnel or the tailnet. The browser must
# also reach Wings directly (below), and Minecraft is raw TCP that the tunnel
# cannot carry. A router port-forward to a node IP is the plan.
apiVersion: v1
kind: Service
metadata:
  name: pelican-panel
  namespace: pelican
  labels:
    app.kubernetes.io/name: pelican-panel
spec:
  type: LoadBalancer
  externalTrafficPolicy: Cluster
  selector:
    app.kubernetes.io/name: pelican-panel
  ports:
    - name: http
      port: 8088
      targetPort: http
---
# ── Wings + game servers on the LAN ──────────────────────────────────────────
# 8080  Wings API. The Panel calls it server-side, AND the browser calls it
#       directly for the console websocket and file uploads — so it has to
#       be reachable from wherever the Panel is used, not just in-cluster.
# 2022  Wings' built-in SFTP server (file access with Panel credentials).
# 25565–25569
#       Game ports. dind publishes each server's port into the pod's network
#       namespace, so the Service just forwards to the pod. Add a port here
#       AND an allocation in the Panel to run more servers.
#
# Same ServiceLB mechanism as above: every node IP answers on every port.
apiVersion: v1
kind: Service
metadata:
  name: pelican-wings
  namespace: pelican
  labels:
    app.kubernetes.io/name: pelican-wings
spec:
  type: LoadBalancer
  externalTrafficPolicy: Cluster
  selector:
    app.kubernetes.io/name: pelican-wings
  ports:
    - name: api
      port: 8080
      targetPort: 8080
    - name: sftp
      port: 2022
      targetPort: 2022
    - name: mc-25565
      port: 25565
      targetPort: 25565
    - name: mc-25566
      port: 25566
      targetPort: 25566
    - name: mc-25567
      port: 25567
      targetPort: 25567
    - name: mc-25568
      port: 25568
      targetPort: 25568

      port: 25569
      targetPort: 25569
```

### Task 2: Wings Deployment with the dind sidecar

**Files:**
- Create: `apps/pelican/wings.yaml` (overwrites the Task 1 stub)

**Interfaces:**
- Consumes: PVCs `pelican-wings-data`, `pelican-docker` (Task 1); Secret `pelican-wings-config` with key `config.yml` (created by hand in Task 3, not in git); Service `pelican-wings` selecting `app.kubernetes.io/name: pelican-wings` (Task 1).
- Produces: Deployment `pelican-wings` listening on 8080 and 2022 inside the pod, with game ports published into the pod namespace by dind.

Design points to preserve while writing it:

- `dind` runs as a **native sidecar**: an `initContainers` entry with
  `restartPolicy: Always`. Kubernetes starts it before the main containers,
  waits for its startup probe, keeps it running, and restarts it if it dies.
  That gives Wings a Docker daemon that is already up when Wings connects,
  instead of a CrashLoop while dind boots.
- The `config` init container copies the Secret into an emptyDir so Wings can
  rewrite `config.yml` (it does, when the Panel pushes a config update) —
  Secret mounts are read-only. The Wings image is distroless with no shell,
  hence busybox for the copy.
- `dockerd` gets explicit `--host` flags. The dind entrypoint only injects its
  default `tcp://0.0.0.0:2375` when the first argument is *not* `dockerd`.

- [ ] **Step 1: Write `apps/pelican/wings.yaml`**

```yaml
# ─────────────────────────────────────────────────────────────────────────────
# Pelican Wings — the daemon that runs game servers.
# Image: ghcr.io/pelican/wings:v1.0.0-beta29  (+ docker:28.5.2-dind sidecar)
# Ports: 8080 API, 2022 SFTP, 25565-25569 game servers (published by dind)
# Data:  /var/lib/pelican (Longhorn PVC), /var/lib/docker (Longhorn PVC)
#
# WHY TWO CONTAINERS. Wings starts every game server as a Docker container
# through the Docker Engine API; it does not speak containerd. The nodes run
# k3s on containerd and have no Docker daemon. So this pod carries its own:
# the dind sidecar runs a private dockerd on 127.0.0.1:2375 and Wings talks
# to that. Game containers therefore live INSIDE the dind container's cgroup,
# which is why dind carries the big resource limits — they cap everything
# Wings launches, and the kubelet's view of node memory stays honest.
#
# WHY dind IS PRIVILEGED. dockerd needs to mount overlayfs, create cgroups,
# and manage iptables in the pod's network namespace. There is no unprivileged
# way to do that. This is the only privileged workload in the cluster that
# runs third-party code on demand (install scripts, server jars). The Docker
# API is bound to loopback so nothing outside the pod can reach it.
#
# WHY TWO MOUNTS APPEAR IN BOTH CONTAINERS AT THE SAME PATH. Wings does not
# copy files into game containers; it tells dockerd to bind-mount
# /var/lib/pelican/volumes/<uuid> and /tmp/pelican/<uuid>/install.sh, and
# dockerd resolves those paths in ITS OWN mount namespace. If the paths differ
# between the two containers, or exist in only one, every install fails with
# an empty or missing directory.
#
# Required secret (create out-of-band — NOT in git). Generated by the Panel
# after you create a Node; see README.md:
#
#   kubectl -n pelican create secret generic pelican-wings-config \
#     --from-file=config.yml=./config.yml
#
# Until it exists the pod sits in Init:0/2 (FailedMount: the Secret is missing). Expected.
# ─────────────────────────────────────────────────────────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pelican-wings
  namespace: pelican
  labels:
    app.kubernetes.io/name: pelican-wings
spec:
  replicas: 1
  # Two ReadWriteOnce PVCs — never two pods at once.
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app.kubernetes.io/name: pelican-wings
  template:
    metadata:
      labels:
        app.kubernetes.io/name: pelican-wings
    spec:
      nodeSelector:
        kubernetes.io/arch: amd64
      # Give running Minecraft servers time to save worlds. Wings forwards
      # SIGTERM as a stop to each server.
      terminationGracePeriodSeconds: 120
      initContainers:
        # ── 1. Copy the Secret into a writable location ────────────────────
        # Secret mounts are read-only; Wings rewrites config.yml when the
        # Panel pushes an updated configuration. The Wings image is distroless
        # (no shell), so busybox does the copy.
        - name: config
          image: busybox:1.37
          imagePullPolicy: IfNotPresent
          command: ["sh", "-c", "cp /secret/config.yml /etc/pelican/config.yml"]
          volumeMounts:
            - name: config-secret
              mountPath: /secret
              readOnly: true
            - name: config
              mountPath: /etc/pelican
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              cpu: 100m
              memory: 32Mi
        # ── 2. Docker daemon, as a native sidecar ──────────────────────────
        # restartPolicy: Always in initContainers makes this a sidecar: it
        # starts before the main containers, must pass its startup probe
        # before they begin, and is restarted if it dies. So Wings never
        # starts against a daemon that is not there yet.
        - name: dind
          image: docker:28.5.2-dind
          imagePullPolicy: IfNotPresent
          restartPolicy: Always
          # Explicit --host flags. The image entrypoint only adds its own
          # default listener (tcp://0.0.0.0:2375, unauthenticated, root-
          # equivalent, on the pod IP) when the first argument is NOT
          # "dockerd". Loopback only.
          args:
            - dockerd
            - --host=unix:///var/run/docker.sock
            - --host=tcp://127.0.0.1:2375
          env:
            # Empty string = do not generate certs or insist on TLS.
            - name: DOCKER_TLS_CERTDIR
              value: ""
          securityContext:
            privileged: true
          volumeMounts:
            - name: docker
              mountPath: /var/lib/docker
            - name: wings-data
              mountPath: /var/lib/pelican
            - name: tmp
              mountPath: /tmp/pelican
          # These limits are the cap on ALL game servers combined — they run
          # inside this container's cgroup. Per-server memory is set in the
          # Panel; keep the sum under the limit. The EliteDesks have ~14Gi
          # allocatable and sit at 4-6Gi used.
          resources:
            requests:
              cpu: 500m
              memory: 2Gi
            limits:
              cpu: "6"
              memory: 8Gi
          # `docker info` over the unix socket — proves dockerd is answering,
          # not merely that the process exists.
          startupProbe:
            exec:
              command: ["docker", "info"]
            periodSeconds: 5
            failureThreshold: 24
          livenessProbe:
            exec:
              command: ["docker", "info"]
            periodSeconds: 30
            timeoutSeconds: 10
      containers:
        - name: wings
          image: ghcr.io/pelican/wings:v1.0.0-beta29
          imagePullPolicy: IfNotPresent
          # Wings builds its Docker client from the environment.
          env:
            - name: DOCKER_HOST
              value: "tcp://127.0.0.1:2375"
            - name: TZ
              value: "Europe/Amsterdam"
          ports:
            - name: api
              containerPort: 8080
            - name: sftp
              containerPort: 2022
            # Game ports are published by dind straight into the pod's
            # network namespace; they need no containerPort here.
          volumeMounts:
            - name: config
              mountPath: /etc/pelican
            - name: wings-data
              mountPath: /var/lib/pelican
            - name: tmp
              mountPath: /tmp/pelican
            - name: logs
              mountPath: /var/log/pelican
          resources:
            requests:
              cpu: 50m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
          # TCP only. /api/system needs a bearer token, so an unauthenticated
          # HTTP probe would read the 401 as failure.
          startupProbe:
            tcpSocket:
              port: api
            periodSeconds: 5
            failureThreshold: 24
          readinessProbe:
            tcpSocket:
              port: api
            periodSeconds: 10
          livenessProbe:
            tcpSocket:
              port: api
            periodSeconds: 30
      volumes:
        - name: config-secret
          secret:
            secretName: pelican-wings-config
        - name: config
          emptyDir: {}
        - name: wings-data
          persistentVolumeClaim:
            claimName: pelican-wings-data
        - name: docker
          persistentVolumeClaim:
            claimName: pelican-docker
        # Install scripts are written here by Wings and bind-mounted into the
        # install container by dind. Shared by both, lifetime of the pod.
        - name: tmp
          emptyDir: {}
        - name: logs
          emptyDir: {}
```

````markdown
# Pelican

[Pelican](https://pelican.dev) game panel, for Minecraft servers. Runs on the
three amd64 EliteDesks only. LAN-only for now; going public is a router
port-forward to a node IP, not a change in this repo.

| What | Address |
| --- | --- |
| Panel UI | `http://192.168.0.158:8088` |
| Wings API (the browser talks to this directly, for console + uploads) | `192.168.0.158:8080` |
| SFTP | `sftp://192.168.0.158:2022` |
| Game servers | `192.168.0.158:25565` – `:25569` |

Every node IP works in place of `.158` — k3s ServiceLB claims the ports on
all of them. `.158` is just the one baked into `APP_URL`.

Design: [`docs/superpowers/specs/2026-09-22-pelican-design.md`](../../docs/superpowers/specs/2026-09-22-pelican-design.md).

## Why Wings has a Docker daemon inside its pod

Wings runs every game server as a **Docker container** and speaks only the
Docker Engine API. The nodes run k3s on containerd — no Docker. So the
`pelican-wings` pod carries a privileged `docker:dind` sidecar that runs a
private `dockerd` on `127.0.0.1:2375`, and Wings points `DOCKER_HOST` at it.

Consequences worth knowing:

- Game containers are **inside** the dind container's cgroup. The dind
  container's memory limit (8Gi) is the ceiling for all servers combined.
  Keep the per-server memory you set in the Panel summing to less than that.
- `kubectl get pods` shows one pod, however many servers are running. To see
  the servers: `kubectl -n pelican exec deploy/pelican-wings -c dind -- docker ps`.
- The dind container is `privileged`. The Docker API is bound to loopback
  so no other pod can reach it, but a container escape from a game server
  lands on the host. Stock Minecraft with friends: accepted.

## First-time setup

The Wings config, including its auth token, is generated by the Panel when
you create a Node. So the Panel must be installed first, and the Wings pod
sits in `Init:0/2 (FailedMount: the Secret is missing)` until step 4. That is expected.

1. Push. Argo CD syncs. Wait for the Panel:

   ```bash
   kubectl -n pelican get pods -w
   ```

2. Open <http://192.168.0.158:8088/installer>. Database **SQLite**, cache
   **filesystem**, session **filesystem**, queue **database**. Create the
   admin user.

3. **Admin → Nodes → Create.**
   - FQDN: `192.168.0.158`
   - Communicate over SSL: **off** (the Panel is plain HTTP; the browser
     will refuse an HTTPS websocket from an HTTP page anyway)
   - Daemon port: `8080`, SFTP port: `2022`
   - Memory / disk: whatever you like; these are Panel-side accounting only.
     The real cap is the dind container's limit in `wings.yaml`.
   - After saving, **Allocations** tab: IP `0.0.0.0`, ports `25565-25569`.

4. Node → **Configuration** tab → copy the YAML into a local `config.yml`,
   then:

   ```bash
   kubectl -n pelican create secret generic pelican-wings-config \
     --from-file=config.yml=./config.yml
   rm config.yml
   ```

5. Within a minute the Wings pod goes `2/2 Running` and the Node shows a
   green heart in the Panel. Then **Servers → Create**: pick the Minecraft
   egg, a `0.0.0.0:25565` allocation, and install.

If you ever recreate the Node in the Panel, delete and recreate the Secret,
then `kubectl -n pelican rollout restart deploy/pelican-wings`.
````
